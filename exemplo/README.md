# A reproducible example

This directory contains everything needed to run TopoTrail end to end and check
the result against numbers someone else measured: a small DEM, three points, one
script, and the values that script must print.

Nothing here comes from a third party. The DEM is **synthetic**, written out by
an analytic relief function in `gerar_mde.py`, so it can be redistributed with
the code under the same licence and regenerated bit for bit on any machine. The
field GPS tracks behind the project's published validation figures are *not*
redistributed — they record the search routes of a team looking for species of
interest to illegal collection — and they are not needed to exercise the
software.

## Files

| File | What it is |
|---|---|
| `gerar_mde.py` | Writes `mde.tif` from an analytic surface. No random numbers. |
| `mde.tif` | The DEM: 300 × 300 cells of 30 m (9 × 9 km), EPSG:32723, elevation 791.5–2023.4 m, 207 kB. |
| `origem.geojson` | Origin, at 500900, 7491900 (south-west of the scene). |
| `destino.geojson` | Destination, at 508100, 7499100 (north-east). |
| `intermediario.geojson` | One intermediate destination, on the southern summit, at 506600, 7493700. |
| `executar.py` | Runs the algorithm through Processing in headless QGIS and writes to `saida/`. |

`saida/` is not versioned: it is regenerated by every run.

## Running it

From the repository root:

```sh
python3 exemplo/executar.py
```

The plugin does **not** have to be installed — the script registers the
Processing provider from this checkout. The only requirement is a Python that
can `import qgis.core`: on Linux that is normally the system `python3` with
`python3-qgis` installed; on Windows the `python-qgis.bat` shipped by the QGIS
installer; on macOS the Python inside `QGIS.app`.

The run takes about 6 seconds on an ordinary laptop and prints the measured
values next to the expected ones, ending in `CONFERE` (they match) or
`NAO CONFERE` followed by the ones that differ. Exit status is 0 only when they
all match.

All 52 Processing parameters are written out in full in `executar.py`, each one
commented with whether it is the plugin default. Two are not defaults, and they
are the two that matter for this example:

* `STREAMS_FROM_DEM = True` — drainage extraction is off by default; it is on
  here because it is what produces the seventh product, the crossings layer;
* `VIA_POINTS_FILE` — an intermediate destination, so the example exercises the
  multi-leg route rather than a single origin-to-destination leg.

The interface language is pinned to `pt` inside the script, because the language
decides the class labels written next to the transitability raster. Change it
and the labels change; nothing else does.

### The numbers to check

These are the values `executar.py` compares, measured with TopoTrail **1.3.0**:

| Quantity | Attribute | Expected |
|---|---|---|
| Route length | `compr_m` | **14404.5** m |
| Walking time, Tobler pace | `tempo_h` / `tempo_hms` | **6.48** h — **6h29** |
| Accumulated ascent | `ganho_m` | **982.6** m |
| Accumulated descent | `perda_m` | **663.1** m |
| Highest point on the route | `alt_max_m` | **1551.1** m |
| Watercourse crossings | features in `_travessias.gpkg` | **3** |
| Potential access zones | features in `exemplo.gpkg` | **11** |

Counts must match exactly. Lengths, times and elevations are compared with a
relative tolerance of 0.1%, which absorbs last-digit differences between NumPy
and GDAL versions; anything larger is a real change in behaviour and should be
reported as an issue.

Other values from the same run, useful if you want to look further than the
route. They are not compared automatically, so treat them as orientation rather
than as a contract:

* the route has 436 vertices in 2 legs, starts at 966.5 m and ends at 1285.9 m,
  and its lowest point is 910.8 m. It passes within 21.2 m — half a cell
  diagonal — of each of the three declared points, which is as close as a route
  made of cell centres can pass;
* `tempo_campo_h` is **16.21 h** (16h12). It is the same route rescaled to the
  2.4 km/h median measured in field survey work: Tobler's 6 km/h maximum is an
  unburdened walker on a path, and multiplying the maximum speed by a constant
  divides every cost by it, so the **path does not change** — only the duration;
* the corridor is a 100 m radius buffer, so 200 m wide, covering 2 840 481 m²;
* the eleven zones total 1421.4 ha;
* suitability runs 0.1333 to 0.9704, median 0.6582; relative topographic risk
  runs 0.0154 to 1.0000, median 0.4078;
* transitability, over 90 000 valid cells: **26.30%** class 1, **36.33%**
  class 2, **30.96%** class 3, **6.13%** class 4, **0.27%** class 5. All five
  classes are populated, which is why the escarpment is in the synthetic relief;
* drainage extraction found 932 channel cells, a 35.86 km network, a drainage
  density of 0.443 km/km². The three crossings are a 7.652 km² stream (cost
  ×4), a 1.509 km² headwater channel (×2) and a 3.172 km² stream (×4);
* the cost surface blocked 7798 cells for exceeding `SLOPE_MAX = 55%` and left
  82 202 navigable.

### Warnings you will see, and can ignore

The run prints a handful of GDAL lines like `Warning 1: Ring Self-intersection
at or near point …` and one `Interior is disconnected`. They come from
polygonising the zone mask: cells selected into a zone can touch only at a
corner, and GDAL reports that shape while writing it. The zones are written
anyway, all eleven geometries come back valid, and the run exits 0. It is noise
from the vectorisation step, not a failure.

### On reproducibility

Re-running the example produces **identical raster files byte for byte** and
identical vector geometry and attributes. The GeoPackage *files* do differ
between runs by a few bytes: GeoPackage stores a `last_change` timestamp in its
`gpkg_contents` table. Compare features, not checksums, when you check the
vector outputs.

### Where the transitability legend lives

Worth knowing before you open that raster somewhere other than QGIS, because it
is written in two places. GeoTIFF has no standard slot for category names, so
GDAL puts them in `exemplo_transitabilidade.tif.aux.xml` beside the raster, and
that is the copy QGIS reads to build the legend. The same five labels also go in
as GDAL metadata items — `TOPOTRAIL_CLASSE_1` … `TOPOTRAIL_CLASSE_5` — which the
GTiff driver stores in the `GDAL_METADATA` tag **inside** the `.tif`, next to the
colour table. Check it for yourself:

```sh
cp exemplo/saida/exemplo_transitabilidade.tif /tmp/sozinho.tif   # the .tif alone
gdalinfo /tmp/sozinho.tif | grep TOPOTRAIL_CLASSE
```

The five labels come back from the lone file, in the language the run used.

## Regenerating the DEM

`mde.tif` is versioned so the example works straight from a checkout, but it is
fully derived:

```sh
python3 exemplo/gerar_mde.py
```

The surface is a sum of commented analytic terms — a regional tilt, two massifs,
a corrugation of ridges and talwegs, a meandering main valley, and an
escarpment — chosen so that the scene exercises every stage of the plugin:
drainage has real channels to find, the route has a valley to cross and a
barrier to go round, and all five transitability classes are occupied.

## If you want to check a claim instead of a number

`exemplo_diagnostico_topotrail.log` is one JSON record per stage. It carries the
plugin version, the versions of Python, GDAL and the operating system, every one
of the 52 parameters as they were resolved, and the distribution statistics of
each intermediate raster. Most of the values listed above can be read straight
out of it, and it is the intended way to trace a route in a report back to the
run that produced it.
